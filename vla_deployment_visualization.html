从模型加载到机器人执行，数据形状从头追踪到尾；支持 11 种模型 × 5 种机器人

贯穿全文的故事
vla_infer 是一个 VLA（Vision-Language-Action）推理部署框架。 它将训练好的 VLA 模型（GR00T / TAO / ACT / RDT / SmolVLA / Pi0 等）加载到 Server 端， 在 Client 端连接真实机器人，实时采集 多路摄像头图像 + 关节状态， 发送给 Server 做推理，得到 连续的动作轨迹 chunk， 经过平滑拟合后驱动机器人完成操作。

目前支持 5 种机器人（a2d / mock / navi_wa2 / unitree_g1 / ti5_t170c） 和 3 种部署入口（run_client / run_web_client / action_server）。

B1 入口层：启动脚本如何串起全链路
B1
Server · run_server.py vla_infer/run_server.py
角色
Server 端是 推理大脑（GR00T / TAO / ACT / RDT / Pi0 等 11 种模型均可）。 它不需要知道机器人在哪，只需要：收到 N 张图像 + M 维关节状态 -> 推演 -> 返回 未来动作规划 chunk。
读取 B2 配置 -> 加载 VLA 模型 -> 启动 ZMQ 服务端 -> 进入推理循环。
# 启动链路： parse_args() -> get_vla_server_config() -> override_config_with_args() -> get_model() # 加载模型(mock/act/gr00t_n1/n1_5/n1_6/rdt/smolvla/go1/pi0/pi05/tao) -> ZMQServer() + VLAServer.run() # ZMQ ROUTER + 推理循环 + Rich Live面板
关键参数 --model_type gr00t_n1_5 | tao | act | pi0 | pi05 ... --model_path /path/to/model --embodiment_tag unitree_g1 | a2d_gripper --debug 禁用 Rich 面板 ZMQ 端口 5566 (default_conf.yaml)

B2 配置层：参数从哪里来、怎么影响部署行为
配置体系
vla_infer 的配置采用 三级覆盖 机制：
conf/*.py（Python 硬编码默认值）← default_conf.yaml（持久化 YAML 覆盖）← CLI 参数 / user_conf（运行时覆盖）。
实际加载顺序（以 vla_context.py 为例）：先 get_client_config()，然后 apply_yaml_overrides()，最后 apply_user_config()。
配置文件关键配置项部署影响默认值(conf)
client_conf.pyvision.preprocess.method=resize 图像统一 resize 到 [480,640]（keep_ratio保持宽高比）resize / 480,640 / true
client_conf.pycontroller.period=3.75ms 控制周期：3.75ms = 266Hz3.75
client_conf.pycontroller.wait_time=200ms 两次推理间的等待间隔200
client_conf.pycontroller.gripper_offset=5 手部动作前向偏移量5
client_conf.pyintra_chunk.intra_chunk_mode=fitting chunk 内处理模式：raw/interpolation/fittingfitting
client_conf.pyinter_chunk.inter_chunk_mode=min_jerk chunk 间过渡策略min_jerk
models_conf.pytype / model_path / embodiment_tag 选择哪个模型 + 哪个机器人体态gr00t_n1_5
robots_conf.pyunitree_g1.action_layout 26维动作切片：arm[0:14] hand[14:26]arm.start=0 hand.start=14
client_conf.pyintra_chunk.fitting_deg=4 多项式拟合阶数4
client_conf.pylanguage.auto_mode=False 是否根据 prob_progress 自动切换语言指令false
default_conf.yaml所有参数持久化 运行时实际加载的实际值，覆盖 conf/*.py（YAML文件）
关键原则：vla_infer 的 robots_conf.action_layout 必须与模型训练的 embodiment 配置严格一致。 如果训练时左臂维度是 7、切片范围是 [0:7)，那部署也必须一模一样。
B3 通信层：Client-Server 的 ZMQ 请求应答
B3
ZMQ 通信 vla_infer/server/core/zmq_server.py
通信流
Client 和 Server 之间通过 ZMQ DEALER/ROUTER 模式异步通信：
Client 收集好 N 张图像 + M 维关节状态 → pickle序列化 + json元数据 → DEALER 异步发送 → Server ROUTER 收到 → 并行解码 + 推理 → ZMQ 回复 → Client DEALER 收到 动作 chunk。
支持 request_id 去重（stale response 自动丢弃）、HWM=1、心跳保活（heartbeat_interval=1s, timeout=30s）。
请求包 pickle(obs+state+language) + json(meta.request_id) 响应包 pickle(pred_action+ext) + json(meta.avg_infer_time) 通信协议 ZMQ.DEALER(Client) / ROUTER(Server)
步骤谁做什么数据形状
1Client Robot 采集观测 → 预处理（resize [480,640]）→ JPEG编码 N张[JPEG] + state[M]
2Client ZMQ DEALER 非阻塞发送 sendMessage(data, meta) 序列化 pickle + JSON multipart
3Server ROUTER 收包 → 并行解码 → pad_and_resize(640) → model.infer() N×[640,640]→[224,224] + state[M]
4Server 异步回调 inference_callback 返回结果 pred_action[64,dim] + ext(prob_progress等)
5Client 收到后 IntraChunk拟合 + InterChunk过渡 → 控制机器人 拟合后[266Hz, dim]
关键约束：ZMQ 通信量为图像编码+pickle耗时；HWM=1 保证不会堆积旧消息。 Server 通过 ThreadPoolExecutor 并行解码多路图像（max_decode_workers）， 推理也通过 max_infer_workers 线程池执行。Client 端通过 request_id 匹配请求-响应， stale response 自动丢弃。
B4 Server 推理层：模型输入输出与三级尺寸映射
B4
Server 推理流程 server/core/vla_server.py
Server 收到数据后做什么
当 Server 收到 Client 发来的观测数据后，inference() 方法做 4 件事：
1. 并行解码：ThreadPoolExecutor 并行解码所有 cam.* 图像
2. pad_and_resize(640,640)：统一到传输口径
3. 模型推理：executor.submit(model.infer, data)，异步 callback 返回
4. 回调回复：inference_callback 通过 ZMQ sendMessage 返回结果

Server 当前支持 11 种模型类型：
mock, act, gr00t_n1, gr00t_n1_5, gr00t_n1_6, rdt, smolvla, go1, pi0, pi05, tao
video [1,T,3,224,224] state [1,dim] language token_ids 输出 [1,64,dim] + ext
模型具体尺寸（T=历史帧数，dim=动作维度）取决于 conf/models_conf.py 和模型训练配置。
B4
Client 480 → Server 640 → 模型 224 三级映射 client/utils/misc.py + server/core/vla_server.py
最容易混淆的概念——三级映射
Client 配置的 vision.preprocess=[480,640] 是客户端预处理口径，
Server 收到后做 pad_and_resize(640,640) 是统一传输口径，
模型内部的 VideoResize(224,224) 是模型感知尺寸。
# 三级映射链路： Client conf: vision.preprocess.height=480, width=640 ← resize保持宽高比 -> JPEG编码 -> ZMQ发送 -> Server 解码 -> VLAServer._pad_and_resize(target=640,640) ← INTER_AREA缩放到640 -> GR00T transform: VideoResize(224,224) ← 模型内部固定逻辑 -> 最终输入 [1,3,224,224]
常见误解：改 Client preprocess_size 不会改变模型输入尺寸。 模型内部一定会缩到 224。Server 的 pad_and_resize(640) 是固定逻辑。
B5 Client 实时控制层：四线程协同
B5
VLAClientAsync 四线程架构 vla_infer/client/core/vla_client.py
四线程协作
需要 4 个工人同时工作：
观测工不断看（N 路摄像头采集）→ 推理工发请求等回复（内联做轨迹拟合+过渡）→ 控制工按固定频率逐帧驱动电机 → 可视化工推送数据到 Web 面板。
它们共享一块黑板（RDMRealtime Data Manager，四线程间共享数据的中心存储）， 观测工写数据，推理工读数据和写动作（内联拟合+过渡），控制工读结果写执行，可视化工推送监控数据。
推理线程使用 MultiThreadTimer（控制/可视化线程），图片编码使用 ThreadPoolExecutor(4)。
线程函数周期职责关键数据
observe _observe_thread_fun~30Hz 采集 N 路摄像头画面 → resize到[480,640] → JPEG编码 → 写入 RDM N×JPEG编码 + state[M]
inference _inference_first/step按触发（wait_time=200ms） 从 RDM 取最新观测 → ZMQ DEALER 发送 → 取回 action chunk pred_action[64,dim]
trajectory 推理线程内联推理完成后触发 IntraChunk拟合 + InterChunk过渡 （推理线程内联执行，非独立线程） 拟合后[266Hz,dim]
control _control_thread_fun266Hz（3.75ms Timer） 按 266Hz 从 RDM 取当前动作 → action_layout解析 → 限幅 → ROS2 话题下发 ROS2话题[分片]
visualize _visualize_thread_fun266Hz Timer 推送动作/状态数据到 VisualizeServer WebSocket（8765） 动作曲线+状态数据
推理-控制流水线时序（wait_time=200ms）
T+0msobserve 采集第 1 帧inference 等待
T+33msobserve 采集第 2 帧inference 触发 _inference_first（ZMQ→Server）
T+83msobserve 持续采集收到 action chunk → IntraChunk拟合 → InterChunk过渡 → 写入 RDM
T+100ms~control 按 266Hz 逐帧执行，wait_time 过后触发下一轮 inference
关键区分：任何抖动问题，先定位是哪个环节的瓶颈： infer 延迟高 → 看 B4 Server；轨迹跳变 → 看 B7 IntraChunk； chunk切换顿挫 → 看 B7 InterChunk；执行跟不上 → 看 B6 限幅和话题频率。
B6 机器人驱动层：以 Unitree G1（26维）为例
B6
G1 26 维动作切片 robots_conf.py + client/robots/unitree_g1/
26 维分解（配置层 vs 驱动层）
G1 全身的动作被编码成一个 [26] 维度的向量。 配置层（robots_conf.py）分为 2 段：arm[0:14] + hand[14:26]； 实际 驱动层（UnitreeG1Robot.py）在内部切成 4 段发送给 ROS2 话题。 手部带防抖机制，差值小于 50 时不重复发送以防电机过热。
配置层切片驱动层切片自由度控制对象ROS2 话题限幅保护
arm[0:14] action[0:7]7 左臂（肩3+肘2+腕2）/left_arm/joint_pos 相对delta+绝对限幅
action[7:14]7 右臂（肩3+肘2+腕2）/right_arm/joint_pos 相对delta+绝对限幅
hand[14:26] action[14:20]6 左手手指（little~thumb_rot）/left_hand_cmd (JointState) 差分防抖≥50
action[20:26]6 右手手指（little~thumb_rot）/right_hand_cmd (JointState) 差分防抖≥50
# 限幅配置（default_conf.yaml）： left_arm_delta: [0.15,0.15,0.15,0.15,0.50,0.25,0.20] right_arm_delta: [0.20,0.15,0.15,0.15,0.50,0.25,0.20] hand_diff_threshold: 50

B7 轨迹/滤波层：IntraChunk 拟合 + InterChunk 过渡双阶段
B7
IntraChunk（块内）平滑拟合 client/core/intra_chunk_smoother.py
从稀疏到密集
Server 返回的 [64,dim] 步动作像简笔画的关键点（≈64帧）， 需要 IntraChunkSmoother 变成连续平滑的线条（266Hz）。 支持 3 种模式：raw（原样输出）、interpolation（线性插值）、fitting（多项式拟合，默认）。 关节和手部分别用不同的拟合策略，使用 ThreadPoolExecutor 并行拟合（max_joint_fitting_workers=14, max_hand_fitting_workers=12）。
# 关节拟合（process方法） coeff = polyfit(timestamps, joint_chunk, deg=config.fitting_deg) # deg=4 q = poly1d(coeff)(x) # 位置 v = polyder(coeff)(x) # 速度 a = polyder(polyder(coeff))(x) # 加速度 # 手部拟合（_gripper_traj_fitting，实际对应 hand/step 两种策略） mean = np.mean(gripper_chunk[window_min:window_max]) if mean > max_threshold: gripper = 1.0 elif mean < min_threshold: gripper = 0.0
输入 [64,dim] → fitting_time_step=3.75ms → 输出 [~800, dim]
调参：fitting_deg 越大曲线越贴合原始数据，但高了可能边界震荡。 使用 action_layout 中的 joint_indices 和 step_indices 区分关节与手部/步进拟合策略。
B7
InterChunk（块间）过渡融合 client/core/inter_chunk_fuser.py
两段动作之间的无缝换挡
模型每推理一次产生一段 64 步 的动作（chunk）。 当新 chunk 到来时，InterChunkFuser 负责平滑地从旧 chunk 的末尾过渡到新 chunk 的开头。 支持 4 种策略。
策略原理表现适用场景
min_jerk五次多项式最小加加速度动作最自然，手部不抖默认推荐
search_action在新 chunk 中搜索最佳切入索引适合快速响应，可能微跳快速抓取/避障
smooth_velocityPD 控制器平滑速度（kp·e - kd·v）非常稳定，但略滞后高精度操作
sync同步模式，阻塞等待推理完成严格对齐无跳变调试/测试
切换策略：通过 CLI 参数 --inter_chunk_mode 或修改 conf/client_conf.py。
B8 可视化与运维层：三套可视化系统 + 资源监控
B8
可视化运维（三套系统） visual/ + web_client/ + action_web_vision/ + visualize_server.py
监控室三套方案
vla_infer 提供 三套可视化方案：
① Client 内置 VisualizeServer：VLAClientAsync 启动时自动创建 WebSocket 服务 (port 8765)， `_visualize_thread_fun` 推送动作/状态/图像数据；支持 3 路 camera 二进制流 + joint_data JSON 图表数据
② action_web_vision：纯转发 FastAPI 仪表盘 (port 9000)，通过 ObsDataBridge (port 9001) 接收实时帧， 不创建独立 RobotBody（避免 DDS 域冲突）。支持 GraspDetector 抓取状态显示 + ARM/Hand 关节轨迹 + 资源监控（CPU/GPU/MEM/BW）
③ web_client/：全功能 FastAPI 仪表盘 (port 9000)，包含机器人控制、录制管理、配置编辑
三者共享同一数据源（RDM 或 ObsDataBridge），但服务方式和范围不同。
监控环节入口观察什么异常信号
VisualizeServer(内置) client/core/visualize_server.py WebSocket 推送 3 路图像 + 动作曲线(position/velocity/acceleration) + 状态数据WS 断连 / 数据推送延迟
action_web_vision action_server/action_web_vision/server.py 3 路相机实时流 + ARM/Hand 轨迹 + 抓取状态 + CPU/GPU/MEM 资源监控 图像卡住 / 曲线断崖
web_client(全功能) web_client/server.py 机器人控制/录制管理/配置编辑/实时监控模块无响应
Server 日志 run_server.py (Rich Live / debug) Avg infer time、infer_count、并行解码时间推理耗时突增 / timeout
Client 日志 run_client.py debug + logging 观测可用率、ZMQ 状态、推理周期、task_progress ZMQ断连 / Heartbeat failed
ROS2 话题 ros2 topic echo 关节状态连续输出、手部话题频率、限幅是否激活 话题中断 / 防抖频繁抑制
部署闭环验证：在可视化面板看到 "图像流 → 推理 → 动作曲线 → 实际机器人动作" 一一对应的闭环，才算部署成功。

B9
任务调度框架（ROS2 ActionServer） action_server/
指挥官
当需要执行复杂的多步骤任务时，action_server 就像一个指挥官，把复合任务拆解成一系列原子操作， 每个原子操作由对应 handler 通过 VLA 推理完成。使用 复合键路由： "task:target" 优先匹配，回退到 "task"。

内置组件：GraspDetector（实时监控 set_angle/get_angle 的 thumb_bend 差值判断抓取）、 ObsDataBridge（推送观测到 WS 9001）、VLAContext（共享 ZMQ + RobotBody）。
核心组件
action_dispatcher.py: ROS2 ActionServer，接收 ExecutionUnit action
vla_context.py: 共享 ZMQClient + RobotBody（懒加载）+ 任务进度
action_base.py: 抽象 handler 基类 + TaskResult 错误码
GraspDetector: 实时监控 set/get 角度的 thumb_bend 差值 ≥200° 持续 0.5s 判定抓取
ObsDataBridge: WS 9001 推送观测给 action_web_vision

算法与公式专区
公式
① 关节多项式拟合 intra_chunk_smoother.py::process
q(t) = Σ aₖ·tᵏ, v(t) = dq/dt, a(t) = d²q/dt²
coeff = polyfit(timestamps, joint_chunk, deg=4) q = poly1d(coeff)(x) v = polyder(coeff)(x) a = polyder(polyder(coeff))(x)
公式
② 手部均值窗 + 阈值离散化 intra_chunk_smoother.py
ḡ(i) = mean(g[i-k : i+k]), if ḡ > max_th → 1, if ḡ < min_th → 0
公式
③ Smooth Velocity (PD 平滑) inter_chunk_fuser.py
acc = kp·(target-pos) - kd·vel, vel = clip(vel+acc·dt), pos += vel·dt
公式
④ Min-Jerk / Search Action inter_chunk_fuser.py
min J = ∫ (d³x/dt³)² dt （Min-Jerk）
Min-Jerk 用五次基函数使加加速度最小（默认推荐）。 Search-Action 在候选窗口中搜索与当前速度方向一致性最高的切入索引。

ZeroMQ 消息队列，Client-Server 通信框架，使用 DEALER/ROUTER 模式异步请求-应答

Realtime Data Manager，四线程间共享数据的中心存储（observe/infer/control/visualize）

模型一次推理输出的一整段连续动作序列，形状 [64, dim]

不同 action chunk 间的过渡/拼接策略

最小加加速度轨迹规划，使 chunk 间过渡最自然平滑，默认推荐

TaskLanguageManager

LeRobotDatasetWriter
录制 LeRobot 格式数据（DataRecordManager），可用于后续训练或回放

实时监控 set_angle/get_angle 的 thumb_bend 差值判断抓取状态
ObsDataBridge
在 dispatcher 进程中推送观测数据到 WS 9001，供 action_web_vision 消费

排障
部署阶段排障速查
症状高概率原因先看哪里处理建议
动作抖动/突变 inter_chunk_mode 不适配或平滑参数过激 inter_chunk_fuser.py 先对比 min_jerk 与 smooth_velocity，再调 search_length/fitting_time_step
响应慢 infer 时间过长或模型资源不足 run_server.py live/debug 输出 观察 Avg infer time，必要时降频或换轻量模型
图像断流 相机话题不稳定或时间戳对齐失败 body_robot.py 检查三路 topic 是否持续，验证 head/left/right 数据完整
手部指令无效 防抖阈值过高导致触发抑制 UnitreeG1Robot.py 检查 diff 阈值与输入尺度，必要时降低阈值或调整 gripper_offset
640/224 混淆 把客户端输入尺寸和模型内部尺寸混为一谈 端到端数据流表 统一口径：部署输入看 640，模型感知看 224
ZMQ 首帧超时 ZMQ 连接未就绪或 stale response vla_context.py VLAContext 预创建共享 ZMQ 客户端 + destroy 时排空 stale 消息
排障第一原则：先确认是 推理问题（delay/timeout）还是 控制问题（抖动/断流）。 前者看 B4 Server，后者看 B6/B7。
