B2 配置层：参数从哪里来、怎么影响部署行为
倒水任务中的角色
就像 TAO 训练时有各种配置参数（action_horizon=64, max_action_dim=32）， vla_infer 部署也有自己的参数。这些参数决定了机器人倒水的速度、平滑度和成功率。
配置文件关键配置项部署影响与 TAO 的关系
conf/client_conf.py vision.preprocess.method=resize 图像统一调整到 [480,640]（keep_ratio保持宽高比） 部署口径，模型内后续缩到 224
conf/client_conf.py controller.period=3.75ms 控制周期：3.75ms = 266Hz -
conf/client_conf.py controller.wait_time=200ms 两次推理间的等待，越长动作越迟滞 -
conf/client_conf.py intra_chunk.intra_chunk_mode=fitting chunk 内处理：raw/interpolation/fitting -
conf/client_conf.py inter_chunk.inter_chunk_mode=min_jerk chunk 间过渡策略 -
conf/models_conf.py type / model_path / embodiment_tag 选择哪个模型 + 哪个机器人体态 直接指向 TAO 输出的 checkpoint
conf/robots_conf.py unitree_g1.action_layout 26维动作切片：arm[0:14] hand[14:26] 与 TAO 的 embodiment 完全一致
conf/client_conf.py intra_chunk.fitting_deg=4 多项式拟合阶数 -
conf/client_conf.py language.auto_mode=True 根据 task_progress 自动切换语言指令 需要在 TAO 中训练 prob_progress 输出
conf/default_conf.yaml 所有参数持久化 运行时实际加载的值 可替代 conf/*.py 的默认值
关键原则：vla_infer 的 robots_conf 必须与 TAO 训练的 embodiment 配置严格一致。 如果 TAO 训练时左臂维度是 7、切片范围是 [0:7)，那部署也必须一模一样。 否则会出现"模型输出对但机器人乱动"的问题。
B3 通信层：Client-Server 的 ZMQ 请求应答
B3
ZMQ 通信 vla_infer/server/core/zmq_server.py
倒水任务中的通信流
Client（G1 身体）和 Server（倒水专家大脑）之间通过 ZMQ DEALER/ROUTER 模式异步通信：
Client 收集好 3 张图像 + 26 维关节状态 → pickle序列化 + json元数据 → ZMQ 异步发送 → Server ROUTER 收到 → 并行解码 + 推理 → ZMQ 回复 → Client DEALER 收到 64 步倒水动作。
与 REQ/REP 不同，DEALER/ROUTER 支持并行请求、非阻塞发送和双向元数据传输。
请求包 pickle(obs+state+language) + json(meta) 响应包 pickle(pred_action+ext) + json(meta) 通信协议 ZMQ.DEALER(Client) / ROUTER(Server)
步骤谁做什么数据形状
1Client Robot 采集观测 → 预处理（统一尺寸[480,640]）→ 编码JPEG 3张[JPEG编码] + state[26]
2Client ZMQ DEALER 非阻塞发送 sendMessage(data, meta) 序列化 pickle + JSON multipart
3Server ROUTER 收包 → 并行解码 → pad_and_resize(640) → model.infer() 3×[640,640,3]→[224,224] + state[26]
4Server 返回推理结果（包含动作 + 扩展字段） pred_action[64,26] + ext(prob_progress等)
5Client IntraChunk拟合 + InterChunk过渡 → 控制机器人 拟合后[266Hz,26]
🔑 关键约束：ZMQ 通信量为图像编码+pickle耗时；HWM=1 保证不会堆积旧消息， 新推理结果到来时旧消息自动丢弃。Server 通过 ThreadPoolExecutor 并行解码多路图像（max_decode_workers）， 通过异步回调 inference_callback 回复结果。
B4 Server 推理层：模型输入输出与两级尺寸映射
B4
GR00T N1.5 输入封装 models/gr00t_n1_5.py::infer()
倒水任务中的角色
当 Server 收到 G1 发来的观测数据后，GR00T N1.5NVIDIA 发布的 VLA 基础模型，基于 SigLIP+Qwen3 架构 等模型通过 infer() 方法将原始 obs 打包成模型需要的输入格式。 Server 当前支持 10 种模型类型：mock, act, gr00t_n1, gr00t_n1_5, gr00t_n1_6, rdt, smolvla, go1, pi0, pi05, tao。
核心输入：3 路视频（头顶 + 左腕 + 右腕）、语言指令、26 维关节状态
video [1,T,3,224,224] {T=历史帧数, 3=RGB, 224=模型内尺寸} state [1,26] {14臂+12手} language token_ids {文本编码} 输出 [1,64,26] + ext {64=action_horizon, ext=prob_progress等}
B4
Client 480 → Server 640 → 模型 224 三级映射 client/misc.py + server/vla_server.py + model transform
最容易混淆的概念——现在是三级映射
Client 配置的 vision.preprocess=[480,640] 是客户端预处理口径， Server 收到后做 pad_and_resize(640,640) 是统一传输口径， 模型内部的 VideoResize(224,224) 是模型感知尺寸。 三级尺寸各自独立，理解这一点能避免大量排障困扰！
# 三级映射链路： Client conf: vision.preprocess.height=480, width=640 ← 客户端预处理（resize保持宽高比） -> JPEG编码 -> ZMQ发送 -> Server 解码 -> VLAServer._pad_and_resize(target=640,640) ← 统一到640传输口径 -> GR00T transform: VideoResize(224,224) ← 模型内部固定逻辑 -> 最终输入 [1,3,224,224]
⚠️ 常见误解：有人以为改 Client 的 preprocess_size 就能改变模型输入尺寸， 实际上模型内部一定会缩到 224。如果要改模型输入分辨率，需要修改 TAO 训练时的 data_config， 然后重新训练模型 —— 这不属于部署范畴。Server 的 pad_and_resize(640) 是固定逻辑。
B5 Client 实时控制层：五线程协同
B5
VLAClientAsync 五线程架构 vla_infer/client/core/vla_client.py
倒水任务中的五线程协作 + 新组件
G1 机器人要流畅地完成倒水，需要 5 个工人同时工作：
观测工不断看（3 路摄像头采集）→ 推理工发请求等回复 → 轨迹工（IntraChunk平滑 + InterChunk过渡）→ 控制工按 266Hz 逐帧驱动电机 → 可视化工推送数据到 Web 面板。
它们共享一块黑板（RDMRealtime Data Manager，五线程间共享数据的中心存储）， 观测工写数据，推理工读数据和写动作，拟合工读动作写拟合结果，控制工读拟合结果写执行，可视化工推送监控数据。
此外还有 TaskLanguageManager（根据 prob_progress 自动切换语言指令）和 LeRobotDatasetWriter（录制训练数据）两个辅助组件。

B6 Unitree G1 驱动层：26维→限幅→ROS2话题，arm+hand双段layout
B6
26 维动作切片 robots_conf.py → UnitreeG1Robot.py
倒水任务的 26 维分解（配置层 vs 驱动层）
G1 倒水时全身的动作被编码成一个 [26] 维度的向量。 配置层（robots_conf.py）分为 2 段：arm[0:14] + hand[14:26]； 实际 驱动层（UnitreeG1Robot.py）在内部切成 4 段发送给 ROS2 话题。 手部带防抖机制，差值小于 50 时不重复发送以防电机过热。
配置层切片驱动层切片自由度控制对象ROS2 话题限幅保护
arm[0:14] action[0:7] 7 左臂（肩3+肘2+腕2） /left_arm/joint_pos (Jointpos) 相对delta+绝对限幅
action[7:14] 7 右臂（肩3+肘2+腕2） /right_arm/joint_pos (Jointpos) 相对delta+绝对限幅
hand[14:26] action[14:20] 6 左手手指（little~thumb)） /left_hand_cmd (JointState,带防抖≥50) 差分防抖
action[20:26] 6 右手手指（little~thumb)） /right_hand_cmd (JointState,带防抖≥50) 差分防抖
B6
ROS2 控制话题映射 UnitreeG1Robot.py::send_robot_action()
从数组到物理动作
26 维数组不能直接驱动电机。需要把 action[0:7] 发给左臂的话题， action[7:14] 发给右臂的话题，action[14:20] 发给左手的话题…… 就像把乐谱的 26 条音轨分发给 26 个乐手各自演奏。
# 26维 → 4个ROS2话题 + 安全限幅 # 出处：client/robots/unitree_g1/UnitreeG1Robot.py::send_robot_action() # Step 1: 限幅——相对delta限位 + 绝对安全限位兜底 # 左臂delta: [0.15,0.15,0.15,0.15,0.50,0.25,0.20] # 右臂delta: [0.20,0.15,0.15,0.15,0.50,0.25,0.20] action = _clamp_arm_actions(action, current_arm_state) # Step 2: 切片 + ROS2 发布 left_arm_msg.joint = action[0:7] → /left_arm/joint_pos (Jointpos) right_arm_msg.joint = action[7:14] → /right_arm/joint_pos (Jointpos) left_hand_msg.position = action[14:20] → /left_hand_cmd (JointState, diff≥50才发) right_hand_msg.position= action[20:26] → /right_hand_cmd (JointState, diff≥50才发)
左臂话题 /left_arm/joint_pos {Jointpos 7维} 右臂话题 /right_arm/joint_pos {Jointpos 7维} 左手话题 /left_hand_cmd {JointState 6维} 右手话题 /right_hand_cmd {JointState 6维}
⚠️ 安全限幅双层保护：
相对限幅：单步 action 与当前 state 的偏差不能超过 delta 值。 例如左肩 pitch delta=0.15，超出则被 clamp。
绝对限幅：关节位置的绝对硬限位，即使相对限幅失效也能兜底。
手部防抖：手部新指令与已发送指令的绝对差之和 > 50 时才发送， 防止手指频繁微调导致电机过热。
控制/推理比：RATIO=9（30Hz/267Hz），delta 按比例缩放。
B7 轨迹/滤波层：IntraChunk 拟合 + InterChunk 过渡双阶段
B7
IntraChunk（块内）平滑拟合 client/core/intra_chunk_smoother.py
倒水动作的"描线"过程
Server 返回的 64 步动作像一副"画了关键点"的简笔画（64帧, ≈3秒）， 需要IntraChunkSmoother把它变成连续平滑的线条（266Hz）， 机器人才能流畅地执行。关节和手部分别用不同的拟合策略。 支持 3 种模式：raw（原样输出）、interpolation（线性插值）、fitting（多项式拟合）。
# 关节拟合：多项式插值（intra_chunk_smoother.py::process） coeff = polyfit(timestamps, joint_chunk, deg=config.fitting_deg) # deg=4 q = poly1d(coeff)(x) # 位置 v = polyder(coeff)(x) # 速度（一阶导） a = polyder(polyder(coeff))(x) # 加速度（二阶导） # 手部拟合：均值窗口 + 阈值离散化（intra_chunk_smoother.py::_gripper_traj_fitting） mean = np.mean(gripper_chunk[window_min:window_max]) if mean > max_threshold: gripper = 1.0 # 张开/闭合 elif mean < min_threshold: gripper = 0.0
输入 [64,26] {64=chunk步数} → fitting_time_step=3.75ms {266Hz} 输出 [~800, 26] {~3秒×266Hz}
🔑 调参：fitting_time_step 越小轨迹越密（2.5ms → 400Hz）， fitting_deg 越大曲线越贴合原始数据，但高了可能边界震荡。
使用 ThreadPoolExecutor 并行拟合关节（max_joint_fitting_workers=14）和手部（max_gripper_fitting_workers=2）。
B7
InterChunk（块间）过渡融合 client/core/inter_chunk_fuser.py
两段动作之间的"无缝换挡"
模型每推理一次产生一段 64 步 的动作（chunk）。 当新 chunk 到来时，InterChunkFuser负责平滑地从旧 chunk 的末尾过渡到新 chunk 的开头， 否则就会出现"机器人一下卡顿然后跳变"——就像开车换挡顿挫。
支持 6 种策略：search_action poly smooth_velocity min_jerk bspline sync。
策略原理倒水任务中的表现适用场景
min_jerk 五次多项式最小加加速度 倒水动作最自然，手部不抖 🚰 默认推荐
search_action 在新 chunk 中搜索最佳切入索引 适合快速响应，但可能微跳 快速抓取/避障
smooth_velocity PD 控制器平滑速度（kp·e - kd·v） 非常稳定，但会略微滞后 高精度操作（如倒水到指定水量）
poly 多项式块间过渡 平滑度高 通用场景
bspline B样条曲线拟合 平滑度高，但计算开销大 轨迹录制回放
sync 同步模式，阻塞等待推理完成 严格对齐无跳变 调试/测试
💡 切换策略的方法：run_client.py --inter_chunk_mode smooth_velocity。 对比实验时只改这一个参数，其他固定，用 20-30 秒稳定段判断效果。

B9
任务调度框架（ROS2 ActionServer） action_server/
倒水任务的"指挥官"
当需要执行复杂的多步骤任务（如抓取→递送→放置→复位）时， action_server 就像一个指挥官，把复合任务拆解成一系列原子操作 （init_grasp → grasp → deliver → place → reset）， 每个原子操作由对应 handler 通过 VLA 推理完成。
核心组件
action_dispatcher.py: ROS2 ActionServer，接收 ExecutionUnit action
vla_context.py: VLA 上下文管理（ZMQ 客户端 + 机器人句柄）
action_base.py: 抽象 handler 基类 + 错误码定义
任务 Handler
task_init_grasp.py: 初始抓取姿态
task_grasp.py: 单手/双手抓取（含抓取检测）
task_deliver.py: 递送物体
task_place.py: 放置物体
task_release.py: 释放物体
task_reset.py: 机器人复位
组件功能关键文件
GraspDetector 实时监控手部 set_angle/get_angle 差值判断抓取状态，thumb_bend 差 > 200° 持续 0.5s 判定为抓取 action_dispatcher.py

⚠️ 依赖说明：action_server 依赖 ROS2 action 协议（message_center/ExecutionUnit.action）， 需要先编译对应的 ROS2 消息包。task handler 通过 VLAContext 间接调用 VLAClientAsync 进行推理。

TAO ↔ vla_infer 串联：训练配置如何决定部署行为
同一套倒水任务配置，从 TAO 训练到 vla_infer 部署的全映射
配置项TAO 训练时vla_infer 部署时必须一致？不一致的后果
action_dim 26（14臂+12手） 26（robots_conf.layout） 必须一致 维度不匹配 → 模型输出无法切片 → 机器人乱动或报错
action_horizon 64 64（模型输出固定） 必须一致 训练用 64 部署用 32 → 模型输出形状不对
embodiment Unitree G1 配置 robots_conf.unitree_g1 必须一致 关节编号/范围不同 → 左臂动作为右臂执行
image_size 224×224（VideoResize） 640→224（两级映射） 模型内一致 部署侧 640 只是预处理，模型内部仍是 224
model_type GR00T N1.5（EagleVL） --model_type gr00t_n1_5 必须一致 模型类型不对 → 权重加载失败
language_instruction "pour water into cup" 推理时传入相同指令 语义一致即可 指令差异大 → 模型输出不符合预期动作
chunk_overlap 不适用 inter_chunk_mode 部署特有 纯部署侧参数，训练不涉及
🔑 核心原则：所有与模型结构相关的配置（action_dim、embodiment、model_type） TAO→vla_infer 必须一字不差。纯部署的配置（inter_chunk_mode、fitting_time_step） 不影响模型输出，只影响控制效果，可以自由调优。

算法与公式专区：每个公式的代码落点
公式
① 关节多项式拟合 intra_chunk_smoother.py::process
q(t) = Σ aₖ·tᵏ, v(t) = dq/dt, a(t) = d²q/dt²
# 用 deg=4 多项式拟合 64 步关节位置 coeff = polyfit(timestamps, joint_chunk, deg=4) q = poly1d(coeff)(x) v = polyder(coeff)(x) # → 速度 a = polyder(polyder(coeff))(x) # → 加速度
公式
② 手部均值窗 + 阈值离散化 intra_chunk_smoother.py::_gripper_traj_fitting
ḡ(i) = mean(g[i-k : i+k]), if ḡ > max_th → 1, if ḡ < min_th → 0
mean = np.mean(gripper_chunk[window_min:window_max]) if mean > max_threshold: gripper = 1.0 # 张开 elif mean < min_threshold: gripper = 0.0 # 闭合
公式
③ Smooth Velocity (PD 平滑) inter_chunk_fuser.py
acc = kp·(target-pos) - kd·vel, vel = clip(vel+acc·dt), pos += vel·dt
for each step: error = target - pos acc = kp*error - kd*vel acc = clip(acc, -max_acc, max_acc) vel = clip(vel + acc*dt, -max_vel, max_vel) pos = pos + vel*dt
公式
④ Min-Jerk / B-Spline / Search inter_chunk_fuser.py
min J = ∫ (d³x/dt³)² dt （Min-Jerk）
C(t) = Σ Nᵢ,ₚ(t)·Pᵢ （B-Spline）
Min-Jerk 用五次基函数使加加速度最小（默认推荐）。 Search-Action 在候选窗口中搜索与当前速度方向一致性最高的切入索引，适合快速响应场景。
