贯穿全文的故事（接 TAO 训练文档）
在 TAO 中，你已经用 3 路摄像头（头部+左腕+右腕） 录好的倒水演示视频， 训练好了能输出 26 维动作（14 臂电机 + 12 手指） 的模型。

现在轮到 vla_infer 上场：

B2 配置层：参数从哪里来、怎么影响部署行为
倒水任务中的角色
就像 TAO 训练时有各种配置参数（action_horizon=64, max_action_dim=32）， vla_infer 部署也有自己的参数。这些参数决定了机器人倒水的速度、平滑度和成功率。
配置文件关键配置项部署影响与 TAO 的关系
conf/client_conf.py preprocess_size=[640,640] 客户端图像统一尺寸，部署主口径 TAO 训练时图像原始 640 被 resize 到 224，部署时同样口径
conf/client_conf.py fitting_time_step=3.75 轨迹插值密度：3.75ms 即 266Hz -
conf/client_conf.py inter_chunk_mode=min_jerk chunk 间过渡策略，影响动作平滑度 -
conf/models_conf.py model_type / model_path 选择哪个 TAO 训练好的模型 直接指向 TAO 输出的 checkpoint
conf/robots_conf.py unitree_g1.action_layout 26维动作切片规则：左臂[0:7] 右臂[7:14] 左手[14:20] 右手[20:26] 与 TAO 的 embodiment 配置完全一致
conf/traj_conf.py filter_window_size / thresholds 手部动作防抖和离散化 (0/1) -
关键原则：vla_infer 的 robots_conf 必须与 TAO 训练的 embodiment 配置严格一致。 如果 TAO 训练时左臂维度是 7、切片范围是 [0:7)，那部署也必须一模一样。 否则会出现"模型输出对但机器人乱动"的问题。
B3 通信层：Client-Server 的 ZMQ 请求应答
B3
ZMQ 通信 vla_infer/server/core/zmq_server.py
倒水任务中的通信流
Client（G1 身体）和 Server（倒水专家大脑）之间通过 ZMQ 来回传递消息：
Client 收集好 3 张 640×640 图像 + 26 维关节状态 → 打包序列化 → ZMQ 发送 → Server 反序列化 → 推理 → ZMQ 回复 → Client 收到 64 步倒水动作。
整个过程就像电话通话：Client 先说话，Server 听完回答，挂断后再接下一通。
请求包 obs + state[26] + language 响应包 pred_action[64, 26] 通信协议 ZMQ.REQ/REP
步骤谁做什么数据形状
1Client 采集观测 → 编码图像 → 组装消息 3×[640,640,3] + state[26]
2Client ZMQ sendMessage 序列化后的字节流
3Server ZMQ 收包 → model.infer() [1,3,224,224]×3 + state[26]
4Server 返回推理结果 pred_action[64,26]
5Client 轨迹拟合 + 插值过渡 → 控制机器人 拟合后[266Hz,26]
🔑 关键约束：ZMQ 是同步 REQ/REP，Client 发送后必须等 Server 回复才能发下一条。 因此推理延迟直接影响控制节奏 —— 如果推理耗时 50ms，那控制频率最高只能到 20Hz。
B4 Server 推理层：模型输入输出与两级尺寸映射
B4
GR00T N1.5 输入封装 gr00t_n1_5.py::infer()
倒水任务中的角色
当 Server 收到 G1 发来的观测数据后，GR00T N1.5NVIDIA 发布的 VLA 基础模型，基于 SigLIP+Qwen3 架构，专门用于机器人任务推理 模型的 infer() 方法将原始 obs 打包成模型需要的输入格式。
核心输入：3 路视频（头顶 + 左腕 + 右腕）、语言指令、26 维关节状态
video [1,T,3,224,224] {T=历史帧数, 3=RGB, 224=模型内尺寸} state [1,26] {14臂+12手} language token_ids {文本编码} 输出 [1,64,26] {64=action_horizon, 26=动作维度}
B4
640 → 224 两级尺寸映射 data_config.py::transform()
最容易混淆的概念
Client 配置的 preprocess_size=[640,640] 是部署口径， 模型内部的 VideoResize(224,224) 是模型感知尺寸。 两者都是必经环节，但意义完全不同！
# 两级映射链路： Client conf: preprocess_size=[640,640] ← 你控制的部署参数 -> ZMQ 传输编码后的 640 图像 -> Server 收到后解码 -> GR00T transform: VideoResize(224,224) ← 模型内部固定逻辑 -> 最终输入 [1,3,224,224]
⚠️ 常见误解：有人以为 Client 配 640 模型就能看到 640 的细节， 实际上模型内部一定会缩到 224。如果要改模型输入分辨率，需要修改 TAO 训练时的 data_config， 然后重新训练模型 —— 这不属于部署范畴。
B5 Client 实时控制层：四线程协同
B5
VLAClientAsync 四线程架构 vla_infer/client/core/vla_client.py
倒水任务中的四线程协作
G1 机器人要流畅地完成倒水，需要 4 个工人同时工作：
观测工不断看（3 路摄像头采集）→ 推理工发请求等回复 → 轨迹工把粗糙的动作描精细 → 控制工逐帧驱动电机。
它们共享一块黑板（RDMRealtime Data Manager，实时数据管理器，四线程间共享数据的中心存储）， 观测工写数据，推理工读数据和写动作，轨迹工读动作写拟合结果，控制工读拟合结果写执行。
线程函数周期倒水任务中的职责关键数据
observe _observe_thread_fun ~30Hz 采集 3 路摄像头画面 + 26 维关节状态写入 RDM 3×640×640×3 RGB + state[26]
inference inference_first/step 按触发 从 RDM 取最新观测 → ZMQ 发给 Server → 取回 action chunk pred_action[64,26]
trajectory _traj_fitting 推理后触发 对 64 步动作做多项式拟合 + 手部防抖，生成高频轨迹 拟合后[266Hz,26]
control _control_thread_fun 固定周期 按 266Hz 从 RDM 取当前动作 → 26 维切片 → ROS2 话题下发 ROS2话题[14臂+12手]
倒水任务中的时序示例（假设 Server 推理耗时 50ms）
T+0msobserve 采集第 1 帧inference 等待
T+33msobserve 采集第 2 帧inference 开始推理（第 1 帧 → ZMQ → Server）
T+83msobserve 采集第 3 帧inference 收到 action chunk [64,26]，trajectory 开始拟合
T+100mscontrol 按 266Hz 开始执行第 1 步动作 ...
🔑 关键区分：任何抖动问题，先定位是哪个线程的瓶颈： infer 延迟高 → 看 B4 Server；轨迹跳变 → 看 B7 拟合参数； 执行跟不上 → 看 B6 ROS2 话题频率。
B6 Unitree G1 驱动层：14臂 + 12手 的动作切片与话题映射
B6
26 维动作切片 robots_conf.py → UnitreeG1Robot.py
倒水任务的 26 维分解
G1 倒水时全身的动作被编码成一个 [26] 维度的向量， 就像乐谱上的 26 条音轨，每条控制一个自由度： 14 条臂轨控制大臂小臂的精确位置，12 条手轨控制手指的张开闭合。 模型预测出 64 步动作，每一步都是一个 [26] 维的"切片"。
切片范围自由度控制对象倒水任务中的用途数据类型
action[0:7] 7 左臂（肩3+肘2+腕2） 左手持水杯，定位到杯口位置 float32
action[7:14] 7 右臂（肩3+肘2+腕2） 右手持水壶，执行倾倒动作 float32
action[14:20] 6 左手手指 控制左手指握住杯子的力度 float32 → 0/1
action[20:26] 6 右手手指 控制右手抓握水壶柄的松紧 float32 → 0/1
B6
ROS2 控制话题映射 UnitreeG1Robot.py::send_robot_action()
从数组到物理动作
26 维数组不能直接驱动电机。需要把 action[0:7] 发给左臂的话题， action[7:14] 发给右臂的话题，action[14:20] 发给左手的话题…… 就像把乐谱的 26 条音轨分发给 26 个乐手各自演奏。
# 26维 → 4个ROS2话题 # 出处：client/robots/unitree_g1/UnitreeG1Robot.py left_arm_msg.position = action[0:7] → /left_arm/joint_pos right_arm_msg.position = action[7:14] → /right_arm/joint_pos left_hand_msg.angle = action[14:20] → /left_hand/set_angle (带防抖) right_hand_msg.angle = action[20:26] → /right_hand/set_angle (带防抖)
左臂话题 /left_arm/joint_pos {7维float} 右臂话题 /right_arm/joint_pos {7维float} 左手话题 /left_hand/set_angle {6维,防抖} 右手话题 /right_hand/set_angle {6维,防抖}
⚠️ 手部防抖机制：手部命令带防抖阈值，差值小于阈值时不发送。 防止手指在小范围内频繁开合导致电机过热。阈值由 traj_conf.py 中的 filter_window_size 控制。
B7 轨迹/滤波层：过渡策略、拟合与平滑
B7
Intra-chunk 拟合 client/core/trajectory_generator.py
倒水动作的"描线"过程
Server 返回的 64 步动作像一副"画了关键点"的简笔画（64帧）， 需要轨迹拟合把它变成连续平滑的线条（266Hz）， 机器人才能流畅地执行。关节和手部的处理方式不同。
# 关节拟合：多项式插值（trajectory_generator.py::_joint_traj_fitting） coeff = polyfit(timestamps, joint_chunk, deg=4) q = poly1d(coeff)(x) # 位置 v = polyder(coeff)(x) # 速度（一阶导） a = polyder(polyder(coeff))(x) # 加速度（二阶导） # 手部拟合：均值窗口 + 阈值离散化（_gripper_traj_fitting） mean = np.mean(gripper_chunk[window_min:window_max]) if mean > max_threshold: gripper = 1.0 # 张开/闭合 elif mean < min_threshold: gripper = 0.0
输入 [64,26] {64=chunk步数} → fitting_time_step=3.75ms {266Hz} 输出 [~266×horizon_sec, 26]
🔑 调参：fitting_time_step 越小输出的轨迹越密（比如 2.5ms → 400Hz）， 但拟合计算量也更大。fitting_deg 越大曲线越贴合原始数据，但高了可能边界震荡。
B7
Inter-chunk 过渡策略 realtime_data_manager.py
两段动作之间的"无缝换挡"
模型每推理一次产生一段 64 步 的动作（chunk）。 当新 chunk 到来时，必须平滑地从旧 chunk 的末尾过渡到新 chunk 的开头， 否则就会出现"机器人一下卡顿然后跳变"——就像开车换挡顿挫。
策略原理倒水任务中的表现适用场景
min_jerk 五次多项式最小加加速度 倒水动作最自然，手部不抖 🚰 默认推荐
search_action 在新 chunk 中搜索最佳切入索引 适合快速响应，但可能微跳 快速抓取/避障
smooth_velocity PD 控制器平滑速度 非常稳定，但会略微滞后 高精度操作（如倒水到指定水量）
bspline B样条曲线拟合 平滑度高，但计算开销大 轨迹录制回放
💡 切换策略的方法：run_client.py --inter_chunk_mode smooth_velocity。 对比实验时只改这一个参数，其他固定，用 20-30 秒稳定段判断效果。

环节谁处理输入尺寸输出尺寸说明
① 传感器采集 UnitreeG1Camera.py 原始传感器流 3×[h,w,3] + state[26] 三路相机原始分辨率不同，state 从 /joint_state 拼装
② 客户端预处理 vla_client.py 3×[h,w,3] 3×[640,640,3] pad_and_resize / crop_and_resize 统一到配置尺寸
③ 图像编码 _process_image() 3×[640,640,3] 编码后字节流 JPEG 编码减小传输体积
④ ZMQ 传输 zmq_server.py 打包 obs+state+language 序列化字节 序列化方式：pickle
⑤ Server 解码 vla_server.py 序列化字节 3×[640,640,3] 解码后恢复图像
⑥ 模型 transform gr00t_n1_5.py 3×[640,640,3] 3×[224,224,3] VideoResize 缩放到模型训练尺寸
⑦ 模型推理 ModelVLA.infer() [1,3,224,224]×3 + state[1,26] [1,64,26] 一次推理产生 64 步动作
⑧ 轨迹拟合 trajectory_generator.py [64,26] [~266*3, 26] 3 秒的动作用 3.75ms 步长细化 ~800 帧

TAO ↔ vla_infer 串联：训练配置如何决定部署行为
同一套倒水任务配置，从 TAO 训练到 vla_infer 部署的全映射
配置项TAO 训练时vla_infer 部署时必须一致？不一致的后果
action_dim 26（14臂+12手） 26（robots_conf.layout） 必须一致 维度不匹配 → 模型输出无法切片 → 机器人乱动或报错
action_horizon 64 64（模型输出固定） 必须一致 训练用 64 部署用 32 → 模型输出形状不对
embodiment Unitree G1 配置 robots_conf.unitree_g1 必须一致 关节编号/范围不同 → 左臂动作为右臂执行
image_size 224×224（VideoResize） 640→224（两级映射） 模型内一致 部署侧 640 只是预处理，模型内部仍是 224
model_type GR00T N1.5（EagleVL） --model_type gr00t_n1_5 必须一致 模型类型不对 → 权重加载失败
language_instruction "pour water into cup" 推理时传入相同指令 语义一致即可 指令差异大 → 模型输出不符合预期动作
chunk_overlap 不适用 inter_chunk_mode 部署特有 纯部署侧参数，训练不涉及
🔑 核心原则：所有与模型结构相关的配置（action_dim、embodiment、model_type） TAO→vla_infer 必须一字不差。纯部署的配置（inter_chunk_mode、fitting_time_step） 不影响模型输出，只影响控制效果，可以自由调优。
从训练到部署的完整故事链
TAO 中用 3 路 224×224 图像 + 26 维关节 + "pour water" 指令 训练 GR00T N1.5 模型 → 导出 checkpoint → vla_infer 加载同一模型，部署到真实 G1 机器人上 → 时序对齐 3 路 640 图像（内部再缩到 224） + 读取 26 维 state → ZMQ 发送 → 模型推理 → 返回 [64,26] action chunk → 轨迹拟合 + 平滑过渡 → ROS2 话题发布 → G1 电机执行倒水

算法与公式专区：每个公式的代码落点
公式
① 关节多项式拟合 trajectory_generator.py::_joint_traj_fitting
q(t) = Σ aₖ·tᵏ, v(t) = dq/dt, a(t) = d²q/dt²
# 用 deg=4 多项式拟合 64 步关节位置 coeff = polyfit(timestamps, joint_chunk, deg=4) q = poly1d(coeff)(x) v = polyder(coeff)(x) # → 速度 a = polyder(polyder(coeff))(x) # → 加速度
公式
② 手部均值窗 + 阈值离散化 trajectory_generator.py::_gripper_traj_fitting
ḡ(i) = mean(g[i-k : i+k]), if ḡ > max_th → 1, if ḡ < min_th → 0
mean = np.mean(gripper_chunk[window_min:window_max]) if mean > max_threshold: gripper = 1.0 # 张开 elif mean < min_threshold: gripper = 0.0 # 闭合
公式
③ Smooth Velocity (PD 平滑) realtime_data_manager.py::_smooth_velocity_transition
acc = kp·(target-pos) - kd·vel, vel = clip(vel+acc·dt), pos += vel·dt
for each step: error = target - pos acc = kp*error - kd*vel acc = clip(acc, -max_acc, max_acc) vel = clip(vel + acc*dt, -max_vel, max_vel) pos = pos + vel*dt
公式
④ Min-Jerk / B-Spline / Search realtime_data_manager.py
min J = ∫ (d³x/dt³)² dt （Min-Jerk）
C(t) = Σ Nᵢ,ₚ(t)·Pᵢ （B-Spline）
Min-Jerk 用五次基函数使加加速度最小（默认推荐）。 Search-Action 在候选窗口中搜索与当前速度方向一致性最高的切入索引，适合快速响应场景。
排障对照表：倒水部署中最常见的 5 类问题
排障
🧯 部署阶段排障速查
症状高概率原因先看哪里处理建议
动作抖动/突变 inter_chunk_mode 不适配或平滑参数过激 realtime_data_manager.py 先对比 min_jerk 与 smooth_velocity，再调 search_length/fitting_time_step
响应慢 infer 时间过长或模型资源不足 run_server.py live/debug 输出 观察 Avg infer time，必要时降频或换轻量模型
图像断流 相机话题不稳定或时间戳对齐失败 UnitreeG1Camera.py 检查三路 topic 是否持续，验证 head/left/right 数据完整
手部指令无效 阈值/防抖导致未触发发送 UnitreeG1Robot.py 检查 left_diff/right_diff 阈值与输入尺度
640/224 概念混淆 把客户端输入尺寸和模型内部尺寸混为一谈 端到端数据流表 统一口径：部署输入看 640，模型感知看 224
🔑 排障第一原则：先确认是 推理问题（delay/timeout）还是 控制问题（抖动/断流）。 前者看 B4 Server，后者看 B6/B7。不要混在一起排查。
